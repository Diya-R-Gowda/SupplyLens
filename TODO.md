## 2. Product / business decisions (implemented my recommended default — revisable)

**Carried from Phase 3/4 (still open):**
- **Enrichment data doesn't feed either scoring formula.** No non-speculative signal for how industry/company-size/founding-year should move a score without real product input.
- **Gemini over a paid company-data API for enrichment/ESG/logistics.** No new signup, but accuracy is unverified (see section 4).
- **A keyless GDELT/RSS fallback was not built** for news — only needed if Currents' key/quota becomes a blocker.
- **Health Score's weight table** (25% ESG / 20% logistics / 15% doc completeness / 15% contract health / 25% inverted risk) — now genuinely *editable* per-org as of Phase 5 (`server/models/RiskConfig.js`), but the *defaults* are still the same first-pass, un-tuned values from Phase 4.
- **Manual `riskScore` edits skip the auto-recompute only when `riskScore` is explicitly present in that request.** Unchanged by Phase 5.
- **Digital Twin is compute-on-read, not persisted.** Unchanged — Phase 5's `alerts` field and narrative text are computed the same way, for the same reason.
- **Snapshot retention (100/org, fixed cap) and daily cadence.** Unchanged.

**New this phase:**
- **Weight validation is hard-rejected, not auto-normalized.** `PATCH /org/risk-config` returns 400 if a weight object doesn't sum to 1 (±0.005 float tolerance), rather than silently rescaling whatever was submitted to fit. Chosen because a silent rescale is exactly the "misconfigured org silently produces nonsense scores" failure mode a configurable-weights feature should avoid — a loud rejection with the actual sum in the error is more honest than guessing what the admin meant. Revisit if this proves too strict in practice (e.g. if auto-normalizing with a visible "we adjusted your inputs to X" confirmation turns out to be less friction).
- **RiskConfig is lazily created on first PATCH, not on first GET.** Reading a never-configured org's weights just returns the hardcoded defaults (`isDefault: true`) without writing anything — avoids a placeholder document for every org that never opens the settings panel. First-ever edit is what creates the row.
- **Confidence scale is 0-1 numeric, not low/medium/high.** Composes with the rest of the app's existing 0-100/0-1 scoring conventions and renders as a percentage; a categorical scale would need its own separate display convention. Live-tested and confirmed to genuinely discriminate (Tesla/Siemens: 0.85-1.0 on enrichment/ESG, 0-0.4 on logistics where public data is scarce; a fabricated company name: 0 across the board) — it's not just always maxed out.
- **Confidence values are Gemini's own self-report**, requested via the same prompted-JSON pattern as `sentimentService.js`'s label/score, not derived from token-level logprobs. The Gemini Node SDK's logprobs support is model/tier-limited and measures token likelihood, not semantic confidence in the answer — a self-reported number, imperfect as it is, was judged more useful and more consistent with the sentiment precedent already in the codebase.
- **Default alert thresholds (riskThreshold: 70, healthThreshold: 30) chosen to match RiskBadge/HealthBadge's own existing "red zone" cutoffs** (risk >66, health <34 render red) rather than picking new arbitrary numbers — a breach roughly lines up with what a user would already read as "red" on the badge. Revisable per-org via `PATCH /org/risk-config`.
- **No separate scheduled cron job checks for threshold breaches.** The alert state (`twinService.js`'s `alerts` field, `GET /dashboard/stats`'s `activeAlerts`) is computed fresh from the supplier's *current* persisted score on every read — there's no caching/staleness window a periodic re-check would need to close. A cron job would only add value if there were a push notification channel to fire from at the moment of breach (email/SMS/etc.), which doesn't exist yet — see section 3.
- **A snapshot is taken on a fresh threshold crossing** (`'threshold_breach'` reason), reusing Step 3's existing large-delta snapshot mechanism (`twinSyncService.js`) rather than adding a second cron. When a change is *both* a large swing and a fresh crossing at once (common for a supplier's first-ever score change), the snapshot reason prioritizes `'threshold_breach'` as the more decision-relevant label — found and fixed via live testing, see commit `ca313fb`.
- **Alert thresholds are per-org, not per-supplier or per-category.** A single risk/health cutoff applies to every supplier in an org. Reasonable default for a first pass; per-category thresholds (e.g. logistics suppliers tolerate a different risk band than SaaS vendors) would be a natural but real extension if that granularity turns out to matter.
- **Narrative explanations never claim a factor's own direction caused the overall reported delta's sign** (Explainable AI, `narrativeService.js`) — deliberate, after live testing surfaced that a factor's ranked contribution can point a different direction than the actual capped score movement whenever an earlier change was itself capped, or when several weights are edited at once. The sentence states the observed score movement and the dominant factor's own movement as separate, both-true facts rather than a causal claim that could be technically wrong. See section 4 for the fuller detail.

**New this phase (Phase 6 — Predictive Analytics):**
- **Minimum-data thresholds are hard-coded constants, not per-org configurable, and deliberately conservative.** Per-supplier forecasting requires ≥5 real `RiskHistory`/`HealthHistory` rows spanning ≥24 real hours (`forecastService.js`); compounding-drift detection requires ≥3 rows spanning ≥6 hours in a 14-day window (`anomalyService.js`); sentiment-shift detection requires ≥4 articles in the (hard-capped) 7-day window. All three were chosen to comfortably reject the exact burst pattern the Phase 6 audit found (4 `RiskHistory` rows for one supplier within 0.03 seconds) while still firing on genuinely time-spread real data — confirmed live once real cron activity produced the first qualifying 24h+ spread this session. Not exposed as org settings because there's no product signal yet for what a "looser" or "stricter" org would even want; revisit if real usage suggests otherwise.
- **Forecast `confidenceLevel` is capped at `'medium'`, never `'high'`, in this version — deliberately, not a placeholder.** A hand-rolled linear regression over at most a few dozen points, projecting a hand-tuned 0-100 business score forward, should never claim to be highly confident regardless of how much data accumulates within what this phase can realistically validate. Revisit only after real production usage has run long enough to check the model's actual track record against what really happened.
- **Forecast horizons are fixed at 7 and 30 days, not configurable.** Matches Step 3's Early Warning horizons directly (same numbers, not a coincidence) and keeps the confidence-interval math's "how far past what we've observed are we projecting" reasoning simple. A per-org configurable horizon is a reasonable future ask, not built now absent a request for it.
- **Portfolio forecasting pools every supplier's raw `SupplierSnapshot` rows for the regression fit, not a day-bucketed average.** Day-bucketing was the first design, tried and rejected after live testing showed it collapsed even a data-rich org (25 real snapshot rows) down to 2-3 daily-average points, wrongly failing the same sufficiency gate the raw-points approach correctly passes. The day-bucketed average is still computed and returned (as `historical`, display-only) since a chart of 25 scattered per-supplier points would be unreadable as a portfolio trend line — see `predictiveAnalyticsService.js`'s comments for the full reasoning.
- **A projected-breach alert (Early Warning) explicitly excludes a metric that's already breaching today**, and a compounding-drift alert (Anomaly Detection) explicitly excludes a window that already contains one single change large enough to have tripped Phase 5's own significant-change mechanism. Both are deliberate non-overlap decisions — re-reporting an already-flagged problem under a second alert type would dilute rather than add signal. Confirmed via unit tests, not just code review (see `alertService.js`/`anomalyService.js`).
- **Anomaly/early-warning UI reuses Phase 5's existing `AlertBanner`/`ActiveAlertsPanel` components (new props, new color-coded sections) rather than a fourth notification surface.** Three tiers now share one place: red (confirmed breach), amber (projected breach), violet (anomaly, neither confirmed nor projected). No new component family was introduced for this phase.

**New this phase (Phase 7 — Scenario Simulator):**
- **Business-value fields were added to `Supplier` (`businessImpact.contractValue`, `.estimatedAnnualSpend`, `.criticalityRating`, `.dependencyNotes`), following the exact same pattern as Phase 3's enrichment/Phase 4's ESG-logistics: an AI-generated default until a user overrides it with real data.** `PATCH /suppliers/:id/business-fields` (admin only) sets the real values; `GET /suppliers/:id/business-impact` computes directly from them (`mode: 'real'`, no Gemini call) once either `contractValue` or `estimatedAnnualSpend` is set, and falls back to a Gemini estimate (`mode: 'ai_estimate'`, labeled `"AI-estimated - populate with real data for accuracy"`) until then. The response always states which mode produced it — confirmed live both ways: an unpopulated supplier correctly returned an honest all-null AI estimate (Gemini had no real basis to guess), a supplier with real fields set correctly returned direct math with no Gemini call at all.
- **`criticalityRating` is a 1-5 integer scale, not enum labels** (my call, as the build instructions left it open) — composes numerically (sortable/filterable later) the same way `confidence` (0-1) and every other score in this app does, rather than adding a new categorical-label display convention.
- **Recovery Planning has no real heuristic at all — deliberately.** The audit found zero real signal anywhere (no document-processing-duration field, no historical time-to-replace-a-supplier data), so `recoveryPlanningService.js` doesn't attempt one; it's a Gemini-generated range (e.g. "4 weeks - 12 weeks") fed Step 1's real simulation context (concentration risk, contract status, data completeness), permanently labeled `"AI-estimated range - not a calculation"` regardless of how much data exists — unlike Steps 1/3/4, this label is never conditional.
- **Alternative Supplier Recommendations hard-filters candidates to the same `category`, but treats country/risk-health-proximity/enrichment/ESG/logistics as soft, independently-gated scoring dimensions** — each only counts when the actual data is real on *both* suppliers being compared (risk/health require an actual `RiskHistory`/`HealthHistory` row, not just the untouched schema default; enrichment/ESG/logistics require both to have been populated). Verified live both ways: an unenriched pair scored on category+country only, and after enriching one supplier, the response correctly reported the exact count of candidates each optional dimension was available for.
- **All three new Gemini-backed services (`mitigationService.js`, `businessImpactService.js`'s estimate path, `recoveryPlanningService.js`) re-derive Step 1's failure-simulation context server-side on every call rather than trusting client-supplied context** — same "never trust a client-provided value for a computed result" precedent as every scoring/forecast service in this app, at the cost of a redundant simulation computation per call (cheap - all real-data reads, no Gemini call inside `simulateSupplierFailure` itself).

**New this phase (Phase 8 — Multi-Agent Intelligence):**
- **"Agent" means a scoped, persona-focused Gemini call (or, for ESG/Logistics, no new Gemini call at all), not an autonomous tool-using agent — a deliberate scope decision, not a shortfall.** The audit that preceded this phase found no multi-step tool-calling framework or pattern anywhere in this codebase; every prior AI feature since Phase 3 is a single prompted-JSON call. Building real inter-agent orchestration (a framework, message passing, iterative negotiation) would have been new architectural scope unjustified by this domain's actual need — five different lenses on the same supplier, not agents that need to debate each other.
- **"Agent Collaboration" is implemented as context-passing, not new infrastructure**: the Manager Agent runs the other four fresh (never cached) and passes their real outputs as input context into one final Gemini prompt — the exact pattern already proven twice in Phase 7 (`mitigationService.js`, `recoveryPlanningService.js` re-deriving Step 1's simulation server-side). No new package.
- **ESG and Logistics agents were built as explicitly-labeled, small-scope wrappers rather than skipped, per this project's established pattern of shipping every roadmap item but framing the weaker ones honestly.** Both reuse `enrichEsgData()`/`enrichLogisticsData()` as-is rather than a duplicate near-identical Gemini prompt under a new persona label — the one real addition in each is a deterministic (no extra Gemini call) framing: naming the weakest ESG dimension, or flagging on-time-delivery below an 80% reliability threshold. Labeled "Based on Phase 4 enrichment data - not independent analysis" everywhere they're surfaced (API response, Swagger docs, and UI badge). This is a real, if modest, addition — not manufactured differentiation — but it is *not* independent analysis, and nothing in the product presents it as such.
- **Finance Agent's payment-history/invoice claims are a hardcoded, code-enforced abstention, never a Gemini call, in either businessImpact mode.** This is a categorically different situation from Phase 7's business-impact AI estimate: Gemini can plausibly reason about a company's *public* facts (industry, size, even a typical contract-value range), but has no possible source — public or inferable — for a specific org's *private* transaction history with a specific supplier. Verified live before building: asked plainly, Gemini correctly abstained; asked with the response shape structured to disallow nulls, the same model readily fabricated a specific, confident-sounding, entirely made-up on-time-payment figure. Confirms a prompt-level instruction alone isn't reliable here — see section 4 below for why this is permanent, not a gap to close later.
- **The Manager Agent's `inputs` block labels each underlying agent's real nature (`genuine_synthesis` / `genuine_extraction` / `real_math_or_estimate_plus_hardcoded_abstention` / `focused_lens_restatement`) via fixed, hardcoded tags in code, not by trusting Gemini's prose to get the framing right every time.** The build's own stated priority was that the executive summary must never imply more independent analytical depth than actually exists across the five inputs — enforcing this in code, in addition to instructing it in the prompt, means a client can always render an accurate depth indicator even if a given summary's wording is imperfect.
- **The Manager Agent recomputes all five agents fresh on every call rather than accepting or caching a previous result**, matching the same staleness-avoidance precedent used throughout Phase 7. Costs up to 4-5 Gemini calls per Manager Agent invocation (Risk Analyst, Legal if documents exist, Finance's AI-estimate path if unpopulated, ESG/Logistics if never fetched before) — see section 3 for the quota implication.

**New this phase (Phase 9 — Supply Chain Visualization):**
- **"Supply Network Graph" and "Relationship Explorer" were built as ONE feature — a "Concentration & Redundancy View" — deliberately never labeled a dependency graph anywhere user-facing.** The pre-build audit confirmed no supplier-to-supplier relationship data (parent/child, upstream/downstream, tiering) exists anywhere in this schema; a graph implying that kind of relationship from category/country tags alone would have misrepresented the data, the same category of problem Phase 8 avoided for the Finance Agent, applied to a visualization instead of a number. Every edge is one of two real, traceable relationships: same-category pairs weighted by `similarityService.js`'s real cross-supplier scoring (Phase 7, reused not duplicated), or same-country-but-different-category pairs as a plain grouping fact. See section 4 for what a *true* dependency graph would need.
- **Geographic Map and Risk Heatmap ship at country-level granularity, using a static country-centroid lookup table (`server/data/countryCentroids.json`, 194 countries) — no geocoding API/key.** `Supplier.country` (a 2-letter ISO code) is the only location data anywhere in this schema; every supplier from the same country renders at the same point, and both views' UI copy and Swagger docs say so explicitly rather than implying precise addresses. See section 3 for per-supplier geocoding as a possible future enhancement.
- **The Geographic Map's base map tiles come from OpenStreetMap's public, keyless tile service — a genuinely different concern from supplier location data.** The map's *background* (coastlines, borders, city names) is a live-fetched but free/unauthenticated resource; the *supplier markers* never leave the static centroid table. Library choice: `react-leaflet` over `react-simple-maps` — the latter doesn't yet declare React 19 as a supported peer (would need a forced `--legacy-peer-deps` install), while `react-leaflet@5` declares native React 19 support and installed cleanly.
- **Risk Heatmap was built as a sorted recharts bar chart, not a choropleth map overlay.** A true choropleth needs a real country-boundary GeoJSON dataset (a new asset to vendor in, not just a styling choice) and would render as mostly empty at the current real data reality (1-3 countries represented, confirmed live) — a sorted bar view is honest and legible at any data density, and needed no new dependency (recharts is already used elsewhere in this app).
- **Portfolio-Wide Timeline was built as a NEW merged, multi-supplier chronological feed (`GET /org/timeline`), not another per-supplier vertical list.** The per-supplier timeline (Phase 4, `Timeline.jsx`) and its trend chart (Phase 6) already existed and work correctly — rebuilding either would have been pure restatement, the same risk the Phase 6 audit flagged for Trend Analysis. The genuinely new part is pooling every supplier's events into one org-wide feed, the same "pool across suppliers" precedent as Phase 6's portfolio forecast.
- **Concentration & Redundancy View uses a manual category-grouped-column layout, not a force-directed/auto-layout library (e.g. dagre).** This graph is small and category-grouped by design (nodes bucketed by category, not a large organic network needing physics simulation) — a manual layout is simpler, more legible, and avoids another dependency this data doesn't need.

**New this phase (Phase 10 — Enterprise Readiness):**
- **RBAC deliberately left as the existing 2-role (admin/viewer) model — not expanded to a 3rd role or resource-level permissions.** The pre-build audit found no real product need for finer granularity anywhere in the codebase or in this file's own history; `requireRole(...roles)` is already variadic (technically ready for more roles the moment a real need shows up), so this is a scope decision, not a limitation of the mechanism. Revisit only if a real use case surfaces (e.g. a "read-only auditor" role distinct from `viewer`, or per-supplier assignment).
- **No caching layer (Redis or in-memory) was added — not currently motivated by real usage.** The pre-build audit's honest read was that no endpoint shows real evidence of needing one at current data volume; adding Redis speculatively would be infrastructure with no problem to solve yet, the same "don't build what isn't motivated by real usage" discipline as the RBAC decision above. Revisit if a specific endpoint's real latency under real load ever actually becomes a problem.
- **mongodb-memory-server (a real, ephemeral mongod binary) was chosen over a separate persistent test-DB Atlas cluster for the Jest suite.** Confirmed working in this dev environment before building the rest of the suite around it. No test ever touches the real dev/production Atlas cluster.
- **CI's Automated Testing scope is critical-path, not comprehensive — a deliberate scope decision named explicitly upfront, not a shortfall discovered after the fact.** See section 4 for exactly what's covered vs. deferred.
- **Docker: single-stage Dockerfile for the server, multi-stage for the client.** The server has no build step (plain CommonJS Express), so a second stage would add complexity with no image-size benefit; the client's build-time node_modules (~400MB) genuinely shouldn't ship in the final nginx-served image, so multi-stage there is a real win, not just convention-following.
- **Render chosen over Railway/Fly.io for the one concrete deployment target this phase names.** A single Render Blueprint (`render.yaml`) can define both a Node web service and a static site together; Railway's config is more single-service-oriented and Fly.io's `fly.toml` targets one app per file — either would need two separate configs/deploys for this app's client+server split, Render needs one file.
- **AuditLog records a lightweight action log (who/what/when/target, plus a small action-specific `detail` object) — deliberately not a full before/after field diff.** A complete diff would capture meaningfully more than a first-pass audit trail needs and adds real complexity (deep-diffing arbitrary Mongoose documents) for a benefit no one has asked for yet. Revisit if compliance/support needs ever require reconstructing an exact prior state, not just knowing that a change happened.
- **CORS's local-dev fallback list is a fixed set of 4 origins (Vite dev :5173, Docker-compose client :8080, both at localhost/127.0.0.1)** — covers this repo's two real local-dev paths. A different local port (e.g. `vite preview`'s default :4173) isn't included by design; set `CORS_ORIGIN` explicitly rather than growing this list for every possible local tool.

## 3. Infrastructure / paid tier (needs your account, billing, or both)

- **Gemini API free-tier quota** — still the main constraint if real usage scales up, and Phase 8 makes this more acute than any prior phase: a single Manager Agent run can trigger up to 4-5 Gemini calls at once (Risk Analyst, Legal, Finance's AI-estimate path, ESG/Logistics on a cold first fetch). No batching/caching was added to reduce this — each agent's real-time context matters more than call-count savings for this phase's honesty goals — but this is the clearest candidate if quota pressure becomes a real problem. Pinned to `gemini-3.5-flash-lite`, confirmed with real headroom during all of Phase 3-7's testing.
- **A real ESG/logistics/company-data provider** (if Gemini's best-effort estimates aren't reliable enough — see section 4) would need its own signup and likely a paid tier for useful coverage.
- **Real push notification infrastructure (email, SMS, or websocket/SSE for live in-app push) for alert thresholds.** Phase 5's alert surfacing is deliberately an in-app banner/badge only — nothing pushes to a user who isn't currently looking at the app. If threshold breaches need to reach someone outside the app (e.g. an email the moment a key supplier's risk crosses the line), that needs a new dependency (`nodemailer` or similar) and likely a transactional-email provider signup (SendGrid, Postmark, etc.), or a websocket/SSE layer for live in-app push without a page reload. Worth adding once there's a real "someone needs to know about this within minutes, not the next time they open the dashboard" use case — not needed for the current in-app-only design. Applies equally to Phase 6's new projected-breach and anomaly alerts — same in-app-only surface, same gap.
- **Forecasting will only become meaningfully more confident with real, ongoing production usage over time — this is expected, not a problem to fix now.** The Phase 6 audit found real per-supplier history essentially non-existent (a handful of same-instant test-burst rows); by the time this phase shipped, several real days of cron activity (helped by this session's own cron-reliability fix) had already produced the first genuinely qualifying 24h+-spread data for a few suppliers and one portfolio. That trajectory — sparse and low-confidence today, gradually denser and more trustworthy the longer the app runs for real — is the correct and expected behavior of everything built this phase, not a shortfall. No action needed; just don't expect confident forecasts to appear on day one of real usage, and don't be surprised when `confidenceLevel` starts reading `'medium'` more often after a few real weeks.
- **A geocoding API/key, for per-supplier map precision beyond the current country-level approximation (Phase 9).** Not needed now — the country-centroid table is a real, honest, no-cost solution for "roughly where is this supplier" — but if precise per-supplier positioning on the Geographic Map/Risk Heatmap is ever wanted (e.g. an actual city or street-level marker instead of a shared country point), that requires a geocoding provider (Google Maps Geocoding API, Mapbox Geocoding, OpenCage, etc.), almost certainly a paid tier at any real usage volume, and a new `Supplier.location` field (lat/lng) to store the result — plus a product decision on whether geocoding runs automatically from the existing `country` field (low precision, same as today) or from a new address field a user would have to enter (real precision, but a new required workflow). Worth revisiting only if country-level ever proves genuinely insufficient in practice.

## 4. Known limitations / deferred work

**Carried from Phase 3/4 (still open):**
- Sentiment classification is Gemini-prompted, not a dedicated sentiment model - reasonable but unbenchmarked at scale.
- `countryRisk.json` only covers 7 countries; everything else defaults to a neutral 50.
- No "create supplier" UI still.
- ESG/logistics/enrichment data quality can't be verified against ground truth - no "correct answer" to check an AI-generated estimate against. Labeled "AI-generated - verify independently" in the UI (now with a confidence badge alongside, see below), but that's a UI disclaimer, not a quality guarantee.
- Digital Twin's compute-on-read approach re-sorts/re-scans a supplier's full news/document/history arrays on every request - fine at current volumes, unbenchmarked at real scale.
- No demo-mode data for ESG/logistics/twin/snapshots/health - all real-DB-only.

**New this phase:**
- **Confidence scores are self-reported by Gemini, with no ground truth to verify the confidence value itself against** - same category of problem as the underlying ESG/logistics data, one level up: there's no way to check whether Gemini's "I'm 85% confident" is actually well-calibrated, only whether it's *plausible* (varies sensibly by company, isn't uniformly maxed out) - which is what was tested live. Treat it as a useful relative signal ("the model is more sure about this field than that one"), not an absolute probability.
- **RAG chat answers (`ragService.js`) do not have confidence scores**, deferred per the build plan's own explicit lower-priority ordering. Converting the chat prompt to structured JSON output (needed to extract a confidence field via the same pattern used elsewhere) risks degrading the free-text conversational answer itself - Gemini's JSON mode is more prone to truncating or reformatting longer prose answers than a free-text completion is, and the chat UI currently renders the answer as natural prose, not a parsed object. If this is wanted later, the safer approach is likely a *second*, short Gemini call after the main answer asking it to self-rate its own just-given answer, rather than folding confidence into the same structured call as the answer.
- **A factor's individually-ranked "increased/decreased" direction in a narrative sentence is not guaranteed to match the overall reported delta's sign.** Real, found via live testing (not hypothetical): when an earlier score change was itself capped (`MAX_SCORE_DELTA`), the stored `previousScore` isn't the true raw weighted sum of that row's factors, so diffing against it can rank a factor whose own value/weight moved one direction on a change where the actual score moved the other way. Fixed to never phrase this as causal ("X caused the score to rise") - the sentence states the real delta and the dominant factor's own movement as two separate, both-true facts - but the *reader* still has to understand these are separate claims. A fully rigorous fix (explaining the uncapped raw formula's movement instead of the actual displayed score) was judged more confusing for a v1 explainability feature, not less, and was not built.
- **Health Score's real independence from Risk Score is smaller than the nominal weights suggest for a never-ESG/logistics-refreshed supplier** (carried forward from the previous verification pass, still accurate as of Phase 5 — see `healthScoreService.js`/`riskScoreService.js`; unaffected by Phase 5's changes since the weights are now editable but the *structural* overlap between doc-completeness/contract-health and Risk Score's own docScore/expiryScore inputs is unchanged).
- **Snapshot comparison UI remains a basic side-by-side raw-state view**, unchanged by Phase 5.

**New this phase (Phase 6 — Predictive Analytics):**
- **Sentiment pattern-shift detection can structurally never look back further than 7 days**, because `NewsCache.publishedAt` has a hard 7-day MongoDB TTL (`models/NewsCache.js`, unchanged since Phase 3) — articles are actually deleted, not just filtered out. This isn't a tunable parameter of `anomalyService.js`; it's a ceiling imposed by a schema decision three phases earlier. If a longer sentiment-trend lookback is ever wanted, it requires either extending or removing the TTL (with the storage-growth tradeoff that implies) or persisting a separate, smaller sentiment-only rollup outside the TTL'd collection.
- **The dashboard-wide per-supplier scans (Step 3's `projectedActiveAlerts`, Step 4's `anomalyAlerts`, computed together in `routes/dashboard.js`) run a forecast + two anomaly checks for every non-currently-breaching supplier on every dashboard load — compute-on-read, unbenchmarked at real scale.** Same precedent and same caveat as the Digital Twin's own compute-on-read approach (carried forward from Phase 4/5); fine at current org sizes (tens of suppliers), worth revisiting if an org grows into the hundreds.
- **The "fires correctly on a genuine real-trigger crossing" test case for Step 3 (Early Warning) and Step 4a (compounding drift) could not be produced within this build session** — both require real data spread across real hours/days that a live session can't fabricate by waiting. Verified instead via (a) unit tests against realistic synthetic point arrays covering the exact crossing/exclusion/direction logic, and (b) a full scan of all real suppliers currently carrying enough history to evaluate, confirming zero false positives and correct abstention given today's actual trends. The underlying logic is verified; a real "this actually caught something happening for the first time" moment has not yet occurred and can only occur through real ongoing usage — expected, per the item in section 3 above, not a gap to close artificially.
- **Portfolio-level historical data is itself still substantially clustered around test/development sessions rather than organically spread**, same honest caveat the Phase 6 audit raised before any code was written. The `historical` field in `GET /org/forecast` and the trend charts built on it are correct and will become more representative purely through continued real usage — nothing to fix in the code itself.

**New this phase (Phase 7 — Scenario Simulator):**
- **Every self-reported confidence value produced this phase (mitigation-strategy confidence, business-impact-estimate confidence, recovery-estimate confidence) inherits Phase 5's known limitation: no ground truth to verify the confidence number itself against, only whether it's plausible.** Confirmed live to vary sensibly rather than being uniformly maxed out - e.g. the recovery estimate for a data-rich, well-documented supplier came back at 0.8 confidence, a sparse-data supplier at 0.4, in the same test session - but there's still no way to check whether either number is actually well-calibrated. Same "useful relative signal, not an absolute probability" framing as every other confidence score in this app.
- **Business Impact's real-math mode only activates once a user actually populates `contractValue` or `estimatedAnnualSpend` via `PATCH /suppliers/:id/business-fields` - it will never activate on its own.** Every supplier defaults to the AI-estimate path indefinitely unless someone deliberately enters real numbers; this is the intended design (see section 2), not a gap, but it means Business Impact's "real" mode is expected to see essentially zero real-world use until this becomes a habitual part of onboarding a supplier - unlike Phase 6's forecasting, which improves automatically just from the app running, this one needs a person to type something in.
- **Alternative Supplier Recommendations remains gated by the same sparse-comparable-data reality the pre-build audit found** - live-tested against the current real supplier set and correctly returned `no_alternatives_found` for a sole-category-source supplier, and a real (if thin) comparison for suppliers sharing a category. This will improve automatically as real orgs accumulate more suppliers with populated enrichment/ESG/logistics data - nothing to fix in the code itself, same trajectory as Phase 6's forecasting confidence.
- **`similarityService.js`'s scoring weights (country match, risk/health proximity, enrichment/ESG/logistics bonuses) are hand-picked constants, not tuned against any real outcome data** - there's no historical "did this recommended alternative actually work out" signal to tune against yet, the same category of limitation Phase 6's forecast thresholds started with. Revisit once real usage produces some track record.

**New this phase (Phase 8 — Multi-Agent Intelligence):**
- **ESG/Logistics agents' honest scope limitation is permanent, not a gap to close later.** They are, and are always intended to remain, focused-lens restatements of Phase 4 enrichment data — not independent analysis. If genuinely independent ESG/logistics analysis is ever wanted (e.g. a real third-party ESG rating provider, or real shipment-tracking data), that's a new data-source integration, not an improvement to these two services as designed.
- **Finance Agent's payment-history/invoice abstention is permanent, not a gap to close with a better prompt.** There is no path to a real answer for this without new infrastructure this project doesn't have — an actual invoice/payment-integration (e.g. QuickBooks, an AP/AR system, or a manually-entered payment log) that SupplyLens has never had and doesn't have on its roadmap. Worth naming explicitly as a real future possibility if that capability is ever wanted: it would need its own new model, its own new endpoints, and real user-entered or integrated data — the abstention in this phase's Finance Agent is correct today and will remain correct until that infrastructure exists.
- **The Manager Agent's executive summary is only as honest as its five inputs, and depends on the prompt continuing to instruct Gemini to preserve that distinction correctly on every call.** The `inputs` block (see section 2) is the code-enforced backstop for this, but the free-text `executiveSummary` itself is still a single Gemini call with no independent verification that it never overstates a weaker input's depth — spot-checked live across a rich and a sparse test profile during this phase's build, both correctly reflected the real depth difference, but this hasn't been tested against every possible input combination.
- **Risk Analyst, Legal, Finance, ESG, Logistics, and Manager Agent confidence scores all inherit the same known limitation as every other self-reported confidence value in this app (see the Phase 5 entry above): no ground truth to verify the number itself against, only whether it's plausible.** Not re-tested for calibration this phase beyond confirming it varies sensibly rather than being uniformly maxed out.
- **Manager Agent's per-call cost (up to 4-5 Gemini calls) means it is the slowest and most quota-expensive single endpoint in the app so far.** No timeout/cancellation handling beyond what `asyncHandler`/Express already provide by default — a slow or failing individual agent call fails the whole Manager Agent request rather than degrading gracefully (e.g. returning a partial summary with one agent's section marked unavailable). Acceptable for this phase's scope; worth revisiting if Manager Agent becomes a frequently-used feature in practice.

**New this phase (Phase 9 — Supply Chain Visualization):**
- **Geographic Map and Risk Heatmap granularity is permanently country-level, not a gap that closes with more data.** Unlike Phase 6/7's sparse-data findings (which improve automatically as the app runs), no amount of real usage makes these two views more precise — that requires new geocoding infrastructure (section 3), a genuinely different kind of gap.
- **All four Phase 9 visualizations will look thin until more real suppliers with diverse countries/categories exist.** Confirmed live at build time: the real database held exactly 1 supplier, 1 country, 1 category. Every view (timeline, map, heatmap, concentration graph) is correct and honest at this density — a single point on a map, an empty-looking bar chart, a graph with no edges are all the right, working behavior for genuinely sparse real data, not a bug. Same trajectory as Phase 6/7: this improves automatically as real suppliers are added, nothing to fix in the code itself.
- **Concentration & Redundancy View's edge labels can visually overlap when multiple relationships converge on one node in a dense area.** Confirmed live with 4 real test suppliers producing 3 real edges - the underlying data and edge count were verified correct by hand, but the on-graph text labels for edges near each other in the same visual corridor can be hard to read at default zoom. Not fixed this phase - a real UI polish item, not a data-correctness issue (the Controls (+/-/pan) let a user zoom in to disambiguate manually today). A cleaner fix would likely be moving edge details to hover/click rather than always-on labels; not built now since it's cosmetic, not honesty-affecting.
- **`similarityService.js`'s reused scoring weights (see the Phase 7 entry above) now also drive Concentration & Redundancy View's edge weights, inheriting the same "hand-picked constants, not tuned against real outcome data" limitation** - a same-category edge's "similarity score" is exactly as unvalidated as an Alternative Supplier Recommendation's score, since it's the literal same function.
- **A true supply-chain dependency graph (parent/child suppliers, upstream/downstream tiers) was deliberately not built this phase — it would need new schema this project doesn't have, and more importantly, a data-entry workflow to populate it that doesn't exist either.** Adding a `parentSupplier`/`tier` field to the schema alone would be close to worthless without a real UI for users to actually declare these relationships - shipping the field without the workflow would produce an empty graph, and shipping a graph UI without real data to show would risk exactly the fabrication-adjacent problem this phase's audit was built to avoid. Worth building as a real, deliberate future phase (new schema + a real relationship-editing UI + this graph reading from it) if true multi-tier supply-chain mapping is ever wanted - not a small addition to the current Concentration & Redundancy View.

**New this phase (Phase 10 — Enterprise Readiness):**
- **Automated Testing's honest coverage boundary — critical-path, not comprehensive, stated explicitly rather than implied.** Covered by the real Jest+Supertest suite (41 tests, 5 files, `server/tests/`): the full auth flow (register/login/refresh/logout, including token rotation and rejection of invalid credentials), the `requireRole` RBAC gate in isolation, cross-org 404 isolation across 4 endpoints spanning 4 different route files, and the two purely deterministic scoring/forecast math services (`scoringEngine.applyCappedDelta`, `forecastService`'s data-sufficiency gating and linear regression). **Explicitly NOT covered**, and not claimed to be: any of the Gemini-backed services (enrichment, ESG/logistics, RAG including its answer-confidence self-rating added later, all 5 Phase 8 agents), the news/snapshot cron jobs, document upload/GridFS, the Phase 9 visualization endpoints, or the Phase 10 audit-log/health endpoints themselves. Building comprehensive coverage of all 9 prior phases' features is a real, honestly-sized multi-session effort on its own - this phase's scope was deliberately "make the most-repeated manual checks (auth, RBAC, org-scoping) real and repeatable, plus the two best pure-math unit-test candidates," not "test everything."
- **Client-side testing was explicitly named as a stretch goal in the build instructions and was not built this session** - server critical-path coverage was the stated priority, and that's where the time went. No Vitest/React Testing Library setup exists yet. A real future task, not a silent gap.
- **The `viewer` role exists in the schema and is correctly enforced by `requireRole`, but the app has no real workflow to ever create one.** Found live while verifying the audit-log endpoint's role gate (Step 6): `POST /auth/register` unconditionally creates the caller as `role: 'admin'` of a brand-new org - there is no invite-a-teammate flow, and no endpoint lets an admin change another user's role. Verifying the viewer-403 behavior required a direct one-off DB update, not anything achievable through the real API. This is a real, concrete product gap (a second role that exists but is functionally unreachable), distinct from the "don't add a 3rd role" scope decision above - if multi-user organisations (more than one person per org) are ever a real goal, this needs an invite/role-management flow before the existing `viewer` role means anything in practice.
- **A recurring Windows-vs-Linux `package-lock.json` gotcha surfaced twice this phase and is worth knowing about for any future `npm install` on this repo from a Windows machine.** Installing new server packages (`mongodb-memory-server`'s optional platform-specific transitive deps, specifically) on Windows can write a lockfile that `npm ci` on GitHub's Linux CI runners rejects as out-of-sync, even though the same lockfile installs fine locally. Confirmed for real both times by watching the pushed CI run actually fail at `npm ci`, not assumed. Fix each time: delete `node_modules` + `package-lock.json`, `npm install` fresh, then verify BOTH `npm ci` and the full test suite pass locally before pushing - don't just trust a plain `npm install` after adding a new server dependency.
- **Automated Docker image publishing was added later (`.github/workflows/docker-publish.yml`), not in this phase.** Publishes both images to GHCR on `v*.*.*` tag push (not every `main` push, so every registry image corresponds to a real release), gated behind a build/test check for each image's source first. `frontend/Dockerfile`/`nginx.conf`/`.dockerignore` were created for this - `frontend/` had none until then, only `client/` did.
- **pino-http logs every request header by default (with the redact list from `config/logger.js` covering known-secret fields like `authorization`), not a curated allowlist of headers.** Reasonable for now (redaction is confirmed working live - see Phase 10's commit history), but worth revisiting if request volume/log storage cost ever becomes a real concern, or if a header nobody anticipated turns out to carry sensitive data.

## 5. Test-data hygiene

- **A DB-wide audit (2026-08-08) found every account in the database was leftover synthetic test data — zero real accounts existed.** The pattern: Phase 3 and earlier testing had explicit `cleanup-*.js` scripts and self-cleaned; Phase 5's `test_step1-5_*.js` scripts never got a matching cleanup step, so 23 orgs from that testing sat live in the DB, quietly accumulating real cron-driven history, unnoticed until this audit. 22 were deleted outright (zero or single-instant test data, no value lost).
- **One org was deliberately kept as an intentional fixture, not deleted: `TEST FIXTURE - DO NOT DELETE - sufficient forecast history` (org `6a7490fe907d2be6c01cfab0`, user `keep-forecast-fixture@do-not-delete.test`, supplier `6a7490fe907d2be6c01cfab2`, "Northwind Logistics").** It's the only org where both risk (8 pts / 29.75h real span) and health (7 pts / 29.75h) forecasts genuinely pass `forecastService.js`'s real sufficiency gates — i.e. the only currently-existing example of what a real, non-`insufficient_data` forecast actually looks like. **Any future "clean up all test data" sweep should exclude this org by ID/name/email pattern rather than deleting it along with genuine throwaway test data.**
- **A second, deeper orphaning problem was found the same day, one level up, during the Phase 7 pre-build audit: 60 orphaned `Organisation` documents (16 of them still holding a `Supplier`) going back to Phase 1 (`2026-07-31` through `2026-08-05`), invisible to the audit above because that one only queried the `users` collection.** Root cause: the app has never had a route that deletes a `User` or `Organisation` at all — only `auth.js`'s register endpoint creates them — so every one of these orgs was orphaned by an *external* test-cleanup script (from Phase 1 through Phase 4's own testing, predating even the Phase 5 gap above) that deleted a `User` directly via a raw DB write without also removing its `Organisation`/`Supplier`. Fixed as real, reusable app code rather than another one-off script: `server/services/orgCascadeService.js` (`deleteOrgCascade`, reuses `deleteSupplierCascade` per-supplier rather than re-implementing that cascade). Verified live before and after both an initial 2-org sanity test and the full 58-org cleanup that followed it. All 60 gone; the fixture org above is the only org left in the database. Commit `b2f7c7d`.
- **Phase 9's own testing (10 `phase9_test_*`/`phase9_*test_*` orgs created across all 4 build steps) was cleaned up the same way, in per-step batches rather than one deferred sweep** — `deleteOrgCascade` dogfooded again, each batch verified with a live query before and after. Final state re-confirmed: exactly 1 org (the fixture above), 1 user, 1 supplier. No repeat of the Phase 5/6 cleanup-claim failures.
- **Phase 10's live-verification testing (4 real orgs total, across Security Hardening/Audit Logs/Performance steps: `phase10_security_verify`, `phase10_audit_verify`, `phase10_audit_verify_org2`, `phase10_lazy_*`) was cleaned up the same way** — `deleteOrgCascade` per batch, each verified live before and after (including an explicit `AuditLog` orphan-count check after the audit-logs step, since that was a new collection this phase). The automated Jest suite itself never touches the real dev DB at all (mongodb-memory-server, a separate ephemeral instance per test run - see section 2), so none of its 41 tests ever created real data needing cleanup in the first place. Final state re-confirmed: exactly 1 org (the fixture), 1 user, 1 supplier, 0 `AuditLog` rows.
